# 调研任务：如何用零依赖源码级静态检查阻止「数据层变更绕过唯一写入口」

## 背景（已发生事实，不要重复推导）

- 单仓浏览器扩展（Chrome MV3 + Firefox），原生 ES 模块，零运行时依赖，无打包器（无 Babel/TypeScript/eslint）。
- 架构：所有布局数据变更必须经过一个统一入口 `commit(op, payload)`；op 到实现函数的映射表叫 `mutationHandlers`（tldraw Store 的 put/remove 模式）。handler 只改数据，`commit` 负责墓碑（tombstone）、索引重建、脏标记、可选落盘。
- 布局数据集合：`layout.boxes`、`layout.connections`、`layout.groups`（仅运行时镜像）、`layout._meta.deleted`（墓碑表）、以及每个盒子上的 `children` / `bookmarks` 数组。
- 已发生故障：单条书签删除曾绕过 `commit` 直接对数组 `splice` 然后 fire-and-forget 落盘，未写墓碑；陈旧远端副本经跨标签合并把书签「复活」（P0 数据丢失类）。已修复：新增 `deleteBookmark` handler。
- 残余：拖拽重排书签仍在 handler 外直接对 `bookmarks` 做 splice（先删后插）。另外新增书签（push）也不走 handler。
- 现状约束：没有 ESLint / TypeScript / AST 依赖；门禁脚本一律 `node scripts/*.mjs`，零第三方依赖，exit 非 0 即阻断。已有同类门禁先例：模块导入图门禁（自定义正则解析 import 语句 + 循环检测 + 白名单）、对比度门禁、版本面一致性门禁。
- 团队已明确的规则：不得静默删除检查；豁免必须具名并带理由；不得用「放宽断言」换绿。

## 需要你回答（每问给「推荐 + 理由 + 可核验来源」）

1. 在**没有 AST / 没有 lint 框架**的纯 JavaScript 仓库里，阻止「数据集合变更绕过唯一写入口」的工业成熟做法有哪些？请对比至少三种，并给出各自能捕获与必然漏掉的东西：
   - （a）正则/行级扫描 + 具名豁免注释；
   - （b）把集合封装成只能通过写入口变更的代理对象（Proxy / 冻结 + 显式 setter 端口），在运行时兜底；
   - （c）把写入口做成架构约束（模块边界 + 导入图门禁），使旁路路径在结构上不存在。
   哪一种最适合本项目现状？如果组合使用，推荐的组合与分工是什么？

2. 正则/行级静态扫描这类「廉价门禁」的已知失败模式是什么？特别是：
   - 如何避免大量误报导致门禁被绕过或被人为放宽（工业界如何处理「门禁噪音」）？
   - 如何让豁免既可见又可审计（注释标记 vs 集中清单 vs 基线文件，各自的审计链与腐化风险）？
   - 别名/间接引用（`const a = obj.arr; a.splice(...)`）这类必须靠数据流分析才能判定的情形，工业上怎么处理？
   请给出「门禁自测（negative test / mutation test）」在工业界的标准做法：如何证明门禁真的有牙齿而不是恒真。

3. 对「门禁首次上线时存量违规」应如何处理才是工业标准做法（一次修完 / 基线冻结 + 棘轮 / 逐条具名豁免 + 到期）？请给出推荐，并说明如何防止豁免清单变成永久债务。
