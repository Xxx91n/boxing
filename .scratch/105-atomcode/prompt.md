# 调研任务：flaky 豁免「撤账/复权」判据的工业成熟方案（票 105 / B69 / A-059）

## 背景（已发生的事实，不要重复推导）

一个浏览器扩展仓库（Chrome MV3 + Firefox，Playwright 扩展 e2e，GitHub Actions 三 OS matrix：ubuntu/macos/windows + 独立 data-golden job）。

仓库已有「G-A 残红书面豁免台账」（waiver ledger）机制，规则要点：

- 只允许 flaky / 环境性失败入账；**broken（全签名一致失败）不得豁免**；**never-quarantine 家族（数据完整性 / 迁移往返 / 回滚演练）永不入账**。
- 每条 5 字段：用例名 | 基线 run URL | 失败签名 | 归属票 | 到期。
- **硬到期不得续期**：到期未修 → 主 lane 禁用该用例或删除，并回填处置记录。
- 发行前跑机器校验脚本，逐行比对失败签名与最新基线 run。

已发生的**事故与既有约定**：

1. 曾出现「**撤账过早**」：某 flaky 面在**单次** run 中零出现即被撤账为 closed，随后**下一次** run 中该面**再次出现** → 实证「单 run 零出现」不足以撤账。
2. 某修绿票的验收标准已写死：「**连续 2 个全量 CI run 无同签名复发** ⇒ 关票并出账」。
3. 本仓已用「**同码重跑 corroboration run**」（对同一 commit 再触发一次全量 CI）把「单 run 声明」升级为「**稳定态声明**」（连续 2 个全量 main run 全绿）。
4. 该台账同时承担**发行门禁 G-A** 的证据角色（main 全量 CI 残红清零，或每条残红有书面定谳豁免）。

## 需要你回答的问题（每问都要给「推荐 + 理由 + 来源」）

1. **撤销/复权判据**：工业上把一个 flaky 豁免「出账 / 复权 / un-quarantine / unflake」的判据是什么？具体阈值：**连续多少次全绿 run**？多少次无复现？时间窗多长？（请覆盖 Google 的 rerun 口径、Datadog flaky 管理的自动转 Fixed、GitLab quarantine 退出条件、Chromium 废弃 FLAKY_ 前缀与 gtest_repeat 口径、Azure DevOps、Meta、Dropbox Athena 等，给原话或可定位出处）
2. **「单次 run 零出现」是否足以撤账**？工业上如何防止 premature de-quarantine / premature unflake？（本仓已有此类事故，需要可引用的工程实践来支撑「≥2 次连续全绿」的门槛）
3. **撤账判据如何与 N/B/F 分桶耦合**：flaky（F）可撤账；**broken（B）是否可撤账**（还是只能修或退役）？**never-quarantine（N）是否可撤账**（还是永不出账、只允许修绿）？给出工业依据。
4. **台账到期机制**：**事件到期**（如「下一条全绿 run」）与**时间到期**（如 30 天）的双闸设计；把「**连续绿次数**」写成事件到期阈值的推荐值（N=2 还是更高）与理由。
5. **判据应写在哪个文档层级**：release gate 的 ADR / 测试治理记录 / 台账规则本体？如何避免与既有门禁 ADR（豁免条目 5 字段 + 不得永久豁免 + 每次发行前复查 + N/B 不得豁免）**冲突或语义漂移**？单一真相源（single source of truth）如何组织？
6. **撤账是否必须要求 corroboration（同码重跑）**？corroboration 的工业等价物与最小次数？「对同一 commit 重跑」与「等新的 main run」在语义上有什么差异（哪个更适合作为撤账证据）？
